# AI协作编程技巧和规范

本文用于提供团队与 AI（Codex/Claude/Cursor/Copilot 等）协作的建议做法，目标是：
- 减少返工
- 提高代码可维护性
- 保证实现与 OpenSpec 一致

说明：本文以“建议”为主，不作为硬性制度。若导师或项目负责人有明确要求，以最新要求为准。

## 1. 适用范围

- 适用于 `mvp-template` 新项目的开发全过程
- 适用于需求分析、方案设计、编码、联调、文档与 PR

## 2. 核心原则（建议优先）

1. 先约束后编码：先明确目标、边界、验收标准，再让 AI 动手。
2. 先 OpenSpec 后实现：中大型改动建议先产出 `proposal/design/tasks`。
3. 小步提交：一次只做一个可验证改动，避免“大杂烩”变更。
4. 结果可追溯：所有关键决策写入文档，不依赖聊天记录记忆。
5. 人工兜底：AI 生成代码建议人工 review 与验证。

## 3. 标准协作流程

### 3.1 需求澄清

在给 AI 下指令前，先写清：
- 目标：要解决什么问题
- 范围：改哪些模块，其他模块要经过我确认
- 验收：接口、页面、命令、手测路径
- 限制：兼容性、性能、安全、上线时间

### 3.2 OpenSpec 建模

满足以下任一情况，建议走 OpenSpec：
- 新功能
- 接口/数据结构变更
- 影响线上行为
- 开发预计超过半天

命令：

```bash
./scripts/openspec-new-change.sh <change-id>
```

最小产物：
- `proposal.md`：Why / What / Impact
- `design.md`：方案与取舍
- `tasks.md`：可勾选、可验证任务

### 3.3 AI执行与约束

让 AI 执行时，建议明确要求：
- 先读哪些文件
- 按什么规范改（如 `docs/优雅代码指南.md`）
- 代码建议落到哪个目录
- 改完建议跑哪些命令

### 3.4 验证与交付

建议执行（按需求选用）：

```bash
pnpm lint
pnpm build
pnpm build:backend
pnpm run ci
```

并确认：
- OpenSpec 文档与实现一致
- `docs/api-contract.md` 已同步（若接口变化）
- PR 描述包含 change-id、验证结果、风险点

## 4. 高质量提问模板（推荐复制）

## 4.1 新功能

```text
目标：<一句话描述目标>
范围：只改 <目录/模块>，其他模块要经过我确认
输入输出：<接口/页面/数据结构>
规范约束：遵守 docs/优雅代码指南.md + OpenSpec
验收标准：<命令通过 + 手测路径>
请先：阅读相关文件并给出修改计划，然后直接实施并自检。
```

## 4.2 Bug 修复

```text
现象：<报错/异常行为>
预期：<正确行为>
复现步骤：1...2...3...
怀疑范围：<文件/模块>
要求：先定位根因，再最小改动修复，避免引入行为变化。
完成后：输出根因、改动点、验证结果。
```

## 4.3 重构优化

```text
目标：<可维护性/性能/复用>
不变条件：<接口契约、页面行为>
风险：<兼容性点>
要求：拆分为多个小步骤，每一步可单独验证。
```

## 5. 项目内建议约束（可按团队节奏调整）

1. 前端页面建议不直接写 `axios/fetch`，统一走 `apps/web/src/api/*`。
2. 后端建议统一使用 `internal/http` 中的响应 helpers，并保持 `success/result/errorMessage` 返回结构。
3. 新增接口建议同步更新 `docs/api-contract.md`。
4. 中大型改动建议挂 OpenSpec change-id。
5. 建议避免 AI 在不确认影响范围的情况下批量改动无关文件。

## 6. 安全与合规

- 建议不要把生产密钥、客户数据、隐私信息粘贴给 AI。
- `.env` 建议只提供示例，不提交真实密钥。
- 涉及账号、支付、权限逻辑时，建议人工做安全 review。
- 对 AI 给出的第三方代码片段，建议确认许可证和来源合规。

## 7. 常见反模式（避免）

1. 只说“帮我改一下”，不提供约束和验收标准。
2. 跳过 OpenSpec，直接让 AI 大改。
3. 一次让 AI 改太多模块，导致回归风险不可控。
4. 只看“能跑”，不做 lint/build/联调验证。
5. 让 AI 修改后不复盘，问题重复出现。

## 8. 建议交付清单（PR 前）

1. 代码改动与需求范围一致。
2. OpenSpec 产物完整且已同步进度。
3. 命令验证通过并记录结果。
4. 接口文档已更新（若有变化）。
5. PR 描述包含：目标、改动点、风险、验证。

## 9. 新人建议

- 第一天先用 AI 完成“读代码 + 输出结构图 + 风险点清单”，再动代码。
- 先从小任务开始，建立“提问模板 -> 执行 -> 验证”的稳定节奏。
- 遇到复杂需求，优先让 AI 帮你拆任务，不要直接要完整大实现。
