# 优雅代码指南（Code Excellence Standards）

> 目的：建立贯穿整个项目的代码优雅、可维护性与团队协作的度量标准。
>
> 适用范围：所有 Go 代码（`src/bin/*/`、`src/orm/`、`src/service/`、`src/common/`、`src/sdk/` 等）
>
> 关键目标：
> - ✅ 代码一致性：同模式问题用同样方式解决 
> - ✅ 可读性优先：6 个月后回顾代码不需要重新理解
> - ✅ 显式胜于隐式：意图清晰、边界明确
> - ✅ 可观测性：重要路径有关键日志/指标
> - ✅ 可测试性：关键业务逻辑可独立测试/mock

---

## 1. 命名规范（Naming）

### 1.1 原则
- **清晰表意**：名字应该立即回答"这是什么"，避免缩写与模糊
- **风格一致**：同一维度的概念使用一致的命名模式
- **长度得当**：作用域越大、越公共，名字应更完整；局部变量可简洁

### 1.2 包名（Package）
- 全小写，无下划线
- 单数优于复数（`model` 而非 `models`）
- 名字要体现包的用途
  - ✅ `orm`、`common`、`sdk`、`config`
  - ❌ `util`、`helper`、`base`（太模糊）

### 1.3 接口名（Interface）
- 单方法接口用 `读+动词+er` 的形式
  - `Reader`、`Writer`、`Closer`、`Marshaler`
- 多方法接口用 `名词` 或 `XXXService`
  - `Store`、`Cache`、`Logger`

### 1.4 结构体名（Struct）
- `UpperCamelCase`，公共导出首字母大写
- 避免 `XXXManager`、`XXXHelper` 这类"万能"词汇
- 业务结构体：动词 + 名词（`CreateRequest`、`ListResponse`）
- 数据模型：`UpperCamelCase`（`User`、`Document`、`KnowledgeEntity`）

### 1.5 函数/方法名（Function/Method）
- `UpperCamelCase`（公开）、`lowerCamelCase`（私有）
- 清晰的动词开头
  - 查询：`Get`、`List`、`Find`、`Search`（不用 `Query`）
  - 写入：`Create`、`Update`、`Delete`、`Add`、`Remove`
  - 校验：`Is`、`Has`、`Can`、`Should`
  - 转换：`To`、`From`、`Marshal`、`Unmarshal`
  - 清理：`Clear`、`Flush`、`Reset`
- 避免歧义
  - ✅ `GetUserById`、`CreateDocument` 清晰
  - ❌ `Get`、`Do`、`Process`（太模糊）

### 1.6 变量名（Variable）
- 函数参数：清晰的名字（避免单字母，除非通用如 `i`、`k`、`v`）
- 返回多值时，用清晰的名字而非 `err1`、`err2`
  - ✅ `user, err := GetUser(...)`
  - ❌ `u, e := GetUser(...)` 或 `result1, result2 := ...`
- 局部变量：按作用域大小调整长度
  - 5 行以内的块可用 `u`、`doc`
  - 跨函数部分要用 `user`、`document`
- 常量：大写 + 下划线（`MAX_RETRY`、`DEFAULT_TIMEOUT`）

### 1.7 常见命名陷阱
| 不好 | 原因 | 推荐 |
|------|------|------|
| `func (u *User) GetData() interface{}` | 返回类型太模糊 | `func (u *User) GetProfile() *Profile` |
| `var result, err = ...` | `result` 太通用 | `var user, err = GetUser(...)` |
| `func Do(...)` | 动词太模糊 | `func GenerateReport(...)` |
| `var data []byte` | 不知道是什么数据 | `var imageData []byte` 或 `var encoded []byte` |
| `func GetAll()` | "All" 不明确 | `func ListActive()` 或 `func GetPublished()` |

## 2. 代码组织与结构（Organization）

### 2.1 文件组织
- **单一职责**：一个文件对应一个主要概念或领域
  - ✅ `user_http.go`（用户相关的 HTTP 请求解析与响应编码）
  - ✅ `user_service.go`（用户业务规则）
  - ✅ `user_store.go`（用户持久化）
  - ❌ `api.go`（混合 50+ 个不同领域的 HTTP、业务和持久化逻辑）
- **文件大小**：单个文件不超过 500 行（否则考虑拆分）
- **顺序约定**
  ```go
  // 包声明
  package http
  
  // 导入
  import (...)
  
  // 类型定义（request/response struct）
  type CreateUserReq struct { ... }
  
  // 常量与变量
  const (...)
  
  // 类型定义
  type userHandler struct { ... }
  
  // 函数实现
  func (h *userHandler) createUser(c *gin.Context) { ... }
  func (u *User) String() string { ... }
  ```

### 2.2 函数组织
- **长度控制**：单函数不超过 100 行；超过则考虑拆小函数
- **入参数量**：不超过 5 个；用`struct` 或 `Option` 模式
  ```go
  // ❌ 太多参数
  func Create(name, desc, category string, priority int, parentID uint, ...) error
  
  // ✅ 用结构体
  type CreateOpt struct {
      Name      string
      Desc      string
      Category  string
      Priority  int
      ParentID  uint
  }
  func Create(ctx context.Context, opt CreateOpt) error
  ```
- **提前返回**（Early Return）：减少嵌套
  ```go
  // ❌ 嵌套多层
  if err == nil {
      if user != nil {
          if user.Active {
              // 实际业务逻辑
          }
      }
  }
  
  // ✅ 提前返回
  if err != nil {
      return err
  }
  if user == nil {
      return ErrUserNotFound
  }
  if !user.Active {
      return ErrUserInactive
  }
  // 实际业务逻辑
  ```

### 2.3 包间依赖
- **单向依赖**：避免循环导入
- **分层清晰**
  ```
  routers → service/orm → common/sdk
  (上层依赖下层，不可反向)
  ```
- **内部包**：用 `internal/` 防止跨包滥用
  - ✅ `src/internal/entity/`（仅供本项目内部使用）
  - ✅ `src/internal/cache/`

## 3. 错误处理（Error Handling）

### 3.1 原则
- **显式处理**：不静默忽略错误
- **快速失败**：遇到错误立即返回，避免继续错误的逻辑
- **错误链**：保留调用栈信息便于调试
- **用户友好**：对外返回人类可读的错误消息

### 3.2 错误创建与传播
```go
// ✅ 定义有意义的错误
var (
    ErrUserNotFound    = errors.New("user not found")
    ErrInvalidEmail    = errors.New("invalid email format")
    ErrDuplicateEntity = errors.New("entity already exists")
)

// ✅ 包装错误，保留上下文
if err != nil {
    return fmt.Errorf("failed to fetch user %d: %w", userID, err)
}

// ❌ 丢失信息
if err != nil {
    return err
}

// ❌ 模糊的错误消息
if err != nil {
    return errors.New("error")
}
```

### 3.3 错误分类
- **业务错误**：用户输入/业务规则违反 → HTTP 4xx
  - 使用 `jsonErr(c, http.StatusBadRequest, "invalid parameter")`
- **系统错误**：程序故障/依赖服务故障 → HTTP 5xx
  - 使用 `jsonErr(c, http.StatusInternalServerError, "internal error")`
- **认证/授权**：无权访问 → HTTP 401/403
  - 使用 `jsonErr(c, http.StatusUnauthorized, "unauthorized")`

### 3.4 检查清单
- ❌ 从不检查 `error`
- ❌ 打印后忽略（`_ = fmt.Sprintf(...)`）
- ❌ panic 用于控制流
- ✅ 每个返回 error 的调用都检查
- ✅ 为错误添加上下文（用户 ID、资源 ID 等）

## 4. 日志与可观测性（Observability）

### 4.1 日志级别
- **ERROR**：需要告警的故障（数据库连接失败、外部 API 故障）
- **WARN**：非正常但可恢复的情况（重试、降级、缓存缺失）
- **INFO**：重要业务事件（用户登录、重要操作完成）
- **DEBUG**：开发调试信息（参数值、中间步骤）

### 4.2 日志规范
```go
// ❌ 不好：缺乏上下文
log.Info("user created")

// ✅ 好：包含关键信息
log.Info("user created", "uid", userID, "email", email, "created_at", time.Now())

// ✅ 错误处理时
log.Error("failed to create user", "uid", userID, "err", err)

// ✅ 长操作记录耗时
start := time.Now()
// ... 操作
log.Info("operation completed", "duration_ms", time.Since(start).Milliseconds())
```

### 4.3 关键路径必须有日志
- API 入口：请求参数 + 用户标识
- 外部依赖调用：服务名 + 耗时 + 状态码
- 业务决策点：为什么选择这个分支
- 错误发生：错误类型 + 上下文信息
- 长操作：进度里程碑

## 5. 并发与资源管理（Concurrency）

### 5.1 Goroutine 泄漏防护
- ❌ 启动后台 goroutine 后不关闭资源
- ✅ 用 `context` 传递信号，`defer` 清理资源
  ```go
  func ListenAndBroadcast(ctx context.Context, msgCh <-chan Message) {
      defer closeResources()  // 确保清理
      for {
          select {
          case <-ctx.Done():
              return
          case msg := <-msgCh:
              broadcast(msg)
          }
      }
  }
  ```

### 5.2 互斥锁使用
- ❌ 长时间持有锁
- ✅ 锁保护最小化的临界区
  ```go
  // ❌ 长时间持有
  mu.Lock()
  // 读数据
  // 调用外部 API（可能耗时）
  // 写数据
  mu.Unlock()
  
  // ✅ 分离读写
  mu.RLock()
  data := cache[key]
  mu.RUnlock()
  
  result := callExternalAPI(data)
  
  mu.Lock()
  cache[key] = result
  mu.Unlock()
  ```

### 5.3 上下文传递
- 所有阻塞操作都应接受 `context.Context`
  ```go
  // ✅ 好
  func (s *Service) FetchData(ctx context.Context, id uint) (Data, error)
  
  // ❌ 不好
  func (s *Service) FetchData(id uint) (Data, error)
  ```

## 6. 性能与优化（Performance）

### 6.1 过早优化的危害
- ❌ 猜测性优化（未测量）
- ✅ 有数据支撑：基准测试/profile 表明瓶颈

### 6.2 常见优化机会
- **批量操作**：用 `IN` 而非逐行查询
  ```go
  // ❌ N+1 查询
  for _, id := range ids {
      user := GetUserByID(id)
  }
  
  // ✅ 批量查询
  users := ListUserByIDs(ids)
  ```
- **缓存正确使用**：过期策略 + 缓存更新策略
  - 记得清缓存（创建/更新/删除后）
  - 缓存穿透防护（负值缓存、布隆过滤）
- **连接复用**：数据库连接池、HTTP Keep-Alive
- **避免深拷贝**：用指针传递大对象

### 6.3 指标收集
- 关键 API 的响应时间、成功率
- 数据库查询耗时分布
- 缓存命中率
- 后台任务队列深度

## 7. 安全与最佳实践（Security & Best Practices）

### 7.1 输入验证
- ✅ 所有用户输入都验证
- ✅ 允许列表原则：白名单检查而非黑名单
  ```go
  // ❌ 黑名单（容易遗漏）
  if !strings.Contains(input, "DROP") && !strings.Contains(input, "DELETE") { ... }
  
  // ✅ 白名单
  allowedCategories := map[string]bool{"tech": true, "life": true, "news": true}
  if !allowedCategories[input] {
      return errors.New("invalid category")
  }
  ```

### 7.2 SQL 注入防护
- ❌ 字符串拼接 SQL
- ✅ 参数化查询（GORM 默认使用）
  ```go
  // ✅ 正确
  db.Where("id = ?", userID).First(&user)
  ```

### 7.3 认证与授权
- ✅ 鉴权中间件在路由层显式声明
- ✅ service 层再次验证权限（纵深防御）
  ```go
  // 路由层
  api.Group("/admin").Use(auth.CheckAdmin).GET("/users", ListAllUsers)
  
  // service 层再次验证（万一中间件失效）
  if !authz.CanManageUsers(ctx, currentUser) {
      return ErrForbidden
  }
  ```

### 7.4 敏感数据
- 不在日志中打印密码、token、密钥
- 脱敏用户信息（邮箱显示 `user****@example.com`）
- 秘钥配置用环境变量，不硬编码

## 8. 测试与质量（Testing & Quality）

### 8.1 测试分类
- **单元测试**：不依赖外部资源，快速运行（100ms 以内）
  - Mock 数据库、外部 API
  - 关键业务逻辑必须单测
- **集成测试**：使用真实依赖或 Docker 容器
  - 不在 CI 快速通道，可选运行
- **端到端测试**：完整流程测试
  - 用于重要用户场景

### 8.2 单测最佳实践
```go
// ✅ 清晰的测试名
func TestUserCreation_WithValidInput_ShouldSucceed(t *testing.T)

// ✅ 准备-执行-验证 结构
func TestUserCreation_WithValidInput_ShouldSucceed(t *testing.T) {
    // Arrange（准备）
    mockStore := &MockUserStore{}
    svc := NewUserService(mockStore)
    
    // Act（执行）
    user, err := svc.Create(context.Background(), "john@example.com")
    
    // Assert（验证）
    if err != nil {
        t.Fatalf("unexpected error: %v", err)
    }
    if user.Email != "john@example.com" {
        t.Errorf("email mismatch: got %s, want john@example.com", user.Email)
    }
}
```

### 8.3 覆盖率目标
- **核心业务逻辑**：≥ 80%
- **工具/通用代码**：≥ 50%
- **外部集成**：≥ 30%（通常用 Mock）

### 8.4 代码审查清单
- [ ] 是否有新的复杂业务逻辑？有测试吗？
- [ ] 错误处理是否充分？
- [ ] 日志是否足够调试？
- [ ] 是否有安全隐患（SQL注入、认证/授权）？
- [ ] 性能是否可接受（N+1、大对象传递）？
- [ ] 命名是否清晰？代码是否易读？

## 9. 文档（Documentation）

### 9.1 代码注释
- ❌ 显而易见的注释（如 `i++  // increment i`）
- ✅ 解释"为什么"而非"是什么"
  ```go
  // ❌ 无用
  // Get user
  user := GetUser(id)
  
  // ✅ 有价值
  // Fetch user from cache first, fallback to DB to avoid N+1
  user := GetUser(id)
  ```

### 9.2 公开 API 文档
- 所有导出函数都需要 Godoc 注释
  ```go
  // GetUser retrieves a user by ID.
  // Returns nil if user not found.
  func GetUser(ctx context.Context, id uint) (*User, error)
  ```

### 9.3 复杂逻辑的设计文档
- 为复杂算法/架构决策留下注释和链接
  ```go
  // EntityDedup uses a probabilistic approach (Bloom filter)
  // to detect duplicate entities before expensive DB lookup.
  // Trade-off: small false positive rate << cost of full DB scan.
  // See docs/entity-dedup-strategy.md
  type EntityDedup struct { ... }
  ```

## 10. 检查清单（Checklist）

### ✅ 代码优雅的自我检查
- [ ] **命名**：变量/函数名是否清晰表意？是否有单字母或 `data`、`result` 这类模糊名字？
- [ ] **长度**：函数是否超过 100 行？文件超过 500 行？嵌套深度超过 3 层？
- [ ] **错误**：是否检查了所有 error？有清晰的错误消息吗？
- [ ] **日志**：关键路径有日志吗？有足够信息调试吗？
- [ ] **安全**：用户输入是否验证？是否用了参数化查询？敏感数据是否脱敏？
- [ ] **并发**：goroutine 会泄漏吗？context 是否正确传递？
- [ ] **性能**：是否有 N+1 查询？大对象是否用指针传递？
- [ ] **测试**：核心业务逻辑是否有单测？是否覆盖错误路径？
- [ ] **文档**：公开 API 有 Godoc 吗？复杂逻辑有注释吗？

## 11. 如何应用本标准

### 为新代码设定高标准
- 代码审查时对标本文档
- 新的 PR 默认至少满足本文档 70% 的条目

### 逐步改进既有代码
- 添加功能时顺便优化相关旧代码（只要不超过本次 PR 的范围）
- 定期的"技术债清理"迭代（重命名、拆小函数、补日志等）

### 持续改进标准本身
- 每半年评审本文档，根据团队反馈与项目演进调整
- 更新时必须同步 `AGENTS.md` 等 AI 指令文件
